# ADR 0001: CLI command framework strategy

Status: Accepted
Date: 2026-02-24
Owner: Tooling

## Context

The CLI entrypoint at `tooling/src/cli/index.ts` grew into a large orchestrator.
Recent refactors split options, plugin loading, and pipeline phases into modules.

We evaluated adding a command framework (`commander` or `yargs`) now.

## Decision

Do not introduce `commander` or `yargs` yet.

Keep the current in-repo parser (`tooling/src/cli/options.ts`) and phase orchestration,
because the CLI still behaves as one primary command (`generate`) with flags.

## Rationale

1. Current needs are covered by a table-driven parser without external dependency.
2. We avoid migration risk while stabilizing recent phase/module extractions.
3. A framework is justified when we add real subcommands, not just more flags.

## Triggers to revisit

Re-evaluate this ADR when at least one of these is true:

1. We add subcommands such as `generate`, `inspect`, `cache`, or `doctor` under one CLI binary.
2. We need autogenerated help/man pages per subcommand.
3. We need nested validation/completion patterns that exceed the current parser.

## Consequences

Positive:
1. No behavior change for existing scripts and flags.
2. Lower short-term complexity and migration cost.

Trade-off:
1. The custom parser remains internal code to maintain until subcommands arrive.
